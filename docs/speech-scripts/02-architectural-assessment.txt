--- Part 1 谁在用 · 约 60 秒 · 展示：06 ---

ZH:
先看用例图。
云仓这边主要是仓库管理员：管站点、目的地、客户；导入价表；算运费；做运单应收应付对比；查规则说明。

For the PDA, the main user is the line worker: login, pick a machine, start work, report work, and query.
Two user groups, two UIs.

--- Part 2 逻辑架构 · 云仓 · 约 80 秒 · 展示：02 ---

ZH:
先看云仓逻辑架构图。
CloudWarehouse 是 Modular Monolith：外面一个 ASP.NET Core 应用，里面模块分开：主数据、导入、计价、结算、规则助手。
上面是网页 index.html 和接口。中间算钱在 Pricing.Core。下面用 Dapper 连 SQL Server。
主流程：Excel 进来，导入模块写入规则或账单，计费引擎算钱，页面预览。
规则查询只在旁边查 FAQ，不算正式结算，也不改金额。

EN:
First, the CloudWarehouse logical architecture.
CloudWarehouse is a Modular Monolith:
one ASP.NET Core app, with modules inside for master data, import, pricing, billing, and a rule helper.
On top is the web page and APIs. Fee logic is in Pricing.Core. Data access uses Dapper and SQL Server.
Main flow: Excel in, import writes rules or bills, the fee engine calculates, then the UI shows a preview.
Rule lookup is only a side FAQ. It is not formal billing, and it does not change money.

--- Part 3 DDD 边界 · 约 70 秒 · 展示：05 ---

ZH:
这张图用 DDD 的想法划边界。
我不是说已经做完整领域框架，只是边界要清楚。
云仓里大概有：主数据、导入、计价、结算、助手。
现在还是一个进程、同一个库，模块之间直接调用。
结算用计价结果，但不要反过来把主数据搞乱。

EN:
This diagram uses DDD ideas to draw boundaries.
I do not claim a full domain framework. I only keep clear borders.
Inside CloudWarehouse we have master data, import, pricing, billing, and helper.
Today it is still one process and one database. Modules call each other in process.
Billing uses pricing results. It should not mess up master data.

--- Part 5 为什么不先拆微服务 · 约 80 秒 · 展示：02 或 01a ---

ZH:
为什么选模块化单体？三点。
一，我一个人做，时间紧，微服务部署和维护太贵。
二，结算要整批导入，失败要回滚，同库事务更合适。
三，模块已经分开，以后真要拆还能拆。
什么时候再考虑拆？人多了，导入和计价要分开扩，发布老打架，访问量明显变大。
现在这样是故意选的，不是偷懒。

EN:
Why a Modular Monolith? Three reasons.
One, I work alone with little time. Microservices cost too much to run.
Two, billing needs batch import and rollback. One database transaction fits better.
Three, modules are already split, so we can extract later if needed.
When to split later? Bigger team, independent scale needs, release fights, or much higher load.
This choice is on purpose. It is not laziness.

--- Part 6 机器上怎么跑 · 约 80 秒 · 展示：03 ---

ZH:
看物理图。
演示环境很直接：浏览器到云仓服务端口 5001，再到 SQL Server 端口 1433。
备份主要靠手工备份和脚本重建。
现在没有负载均衡，也没有数据库高可用。
图上灰色框是以后可能加强的，现在没有上线。

EN:
Please look at the physical diagram.
The demo setup is simple: browser to CloudWarehouse on port 5001, then SQL Server on port 1433.
Backup is mostly manual backup and script rebuild.
There is no load balancer, and no database high availability now.
Grey boxes are future ideas. They are not live today.

--- Part 7 部署 · 约 60 秒 · 展示：04 / 21 ---

ZH:
云仓可以打成一个可执行包，或放到 IIS 上跑。
PDA 是另一条线：手持机，内网访问，Spring Boot 比如 8080，再到单独的库。
两条线分开，一个挂了不容易拖死另一个。

EN:
CloudWarehouse can run as one package, or on IIS.
The PDA is another path: handheld device, intranet HTTP, Spring Boot such as port 8080, then its own database.

--- 片尾补录 ADD-ON（旧片直接接这段 · 约 50 秒 · 不用新 PPT，对着镜头说即可）---

ZH:
补一条 Architecture 评分点：Security threats and mitigation。
威胁一：恶意或过大 Excel。缓解：扩展名白名单、大小限制。
威胁二：连接串泄露。缓解：example 配置，真密钥不进 Git，录像也不出示。
威胁三：未授权改价或乱调接口。现状内网演示为主，JWT/角色仍是 Planned。
威胁四：两条系统互相拖垮。缓解：分部署、分库。
这是威胁加缓解，不是生产级安全全做完。谢谢。

EN:
Rubric add-on: security threats and mitigation.
Threat one: bad or oversized Excel. Mitigation: whitelist and size limit.
Threat two: connection-string leak. Mitigation: example config, secrets out of Git, not shown on camera.
Threat three: unauthorized change or open APIs. Mostly intranet demo today; JWT and roles stay Planned.
Threat four: one system taking the other down. Mitigation: separate deploy and separate databases.
Threat plus mitigation — not full production security done. Thank you.
