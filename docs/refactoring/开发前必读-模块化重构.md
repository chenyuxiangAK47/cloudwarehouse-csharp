# 云仓后端模块化重构 — 开发前必读

> **核心目标：**「一份代码，两种交付叙事」  
> **优先级：** 师傅生产交付 **100%** 高于 NUS 学术架构展示。  
> **约束速查：** [`refactor.constraints.ini`](./refactor.constraints.ini)（AI/脚本可读）  
> **本文档版本：** 2026-06（Phase 2 启动前）

---

## 0. 两种交付分别是什么

| 交付对象 | 要什么 | 部署形态 |
|----------|--------|----------|
| **师傅（生产）** | 运单导入、双轨算价、面单费单独列、导出对账、Phase 1 已有功能 | **单 exe** + SQL Server + `启动云仓.bat`，无容器、无第二进程 |
| **NUS（学术）** | DDD 边界、微服务**演进**叙事、可演示的服务拆分 | 报告 + 架构图 + **可选** `Pricing.Api` 小样；**不要求**师傅安装 |

**结论：** 代码可以按模块划分；**运行态永远是模块化单体**。微服务是「设计方向 + 可选 Demo」，不是生产默认。

---

## 1. 最高红线（绝对禁止）

1. **禁止修改存量业务逻辑**  
   双轨算价、取整（向上取整公斤）、面单费、Excel 导入/导出、价目表 upsert — **只允许改文件路径**，不允许改算法、字段含义、SQL 行为。

2. **禁止破坏单体发布**  
   `scripts/publish-self-contained.ps1` → `publish/CloudWarehouse-win-x64-self-contained.zip` → `启动云仓.bat` 流程必须不变；发布目录不得出现 Docker、第二个 exe 依赖。

3. **禁止在主项目引入微服务基础设施**  
   `CloudWarehouse.Backend` 不得添加：Ocelot、Consul、MassTransit、gRPC 客户端调用自家演示服务等。

4. **禁止破坏现有数据访问**  
   当前为 **Dapper + SqlConnection**（非 EF Core）。不拆库、不改 `appsettings.json` 连接串、不为了「服务化」改访问模式。  
   Phase 2 新增 `BillLines` 等表走 **独立 SQL 脚本 + 评审**，不属于本 refactor 步骤 1–3。

---

## 2. 每步铁则

- **原子小步：** 一步只做一件事（例如只移 `PriceCalculator.cs`）。
- **先搜引用：** `rg ClassName` 全 solution 后再移动。
- **改完即编译：** `dotnet build CloudWarehouse.sln -c Release`
- **核心逻辑即测试：** `dotnet test`；算价类对照重构前后数值。
- **兼容优先：** 不新增 Repository 接口层除非已有先例。
- **演示隔离：** `CloudWarehouse.Pricing.Api`（可选）**只引用 Core**；Backend **不得**引用 Api。

**兜底：** 拿不准 → **只新增目录/空项目/文档**，不动存量代码。

## 3. 目标目录结构（终态示意）

```
cloudwarehouse-csharp/
├── CloudWarehouse.Backend/          # 生产单体（唯一对外 Web + 静态 UI）
│   ├── Program.cs                   # 不改启动/监听逻辑
│   ├── Modules/
│   │   ├── MasterData/              # 站点、目的地、客户、（Phase2）账户
│   │   ├── Pricing/                 # 价目、试算、规则持久化
│   │   ├── Import/                  # 价目表 Excel 导入协调
│   │   └── Billing/                 # Phase2：运单、结算、导出
│   └── Shared/                      # ApiResponse 等横切（可选，后移）
├── CloudWarehouse.Pricing.Core/     # 纯计算类库（无 SQL、无 HTTP）
├── CloudWarehouse.Pricing.Api/      # 【可选】NUS 演示，不进入师傅 zip
├── CloudWarehouse.Tests/
├── CloudWarehouse.IntegrationTests/
├── scripts/publish-self-contained.ps1
└── docs/refactoring/                # 本文档
```

**说明：** Phase 1 文件目前在 `Controllers/`、`Services/`、`Helpers/`、`Models/` 根下；重构是**平移**到 `Modules/*`，不是重写。

## 5. CloudWarehouse.Pricing.Core 边界

**可以放入 Core（无 I/O）：**

- `PriceCalculator`（现有）
- `PriceRuleMapper`（现有）
- 未来的 `WeightRoundingService`（取整，与 Excel K 列公式一致）

**暂不放入 Core（有 SQL / ASP.NET 依赖）：**

- `PriceRuleCalculateService`
- `PriceRuleImportService`
- 所有 `*Controller`、`*ExcelHelper`

**Core 项目约束：**

- Target: `net9.0` class library
- 仅允许 `System.*` 依赖；**禁止** ClosedXML、Dapper、SqlClient
- 被 Backend 项目引用；被 Pricing.Api（可选）引用

- [ ] 验证：`dotnet build` 通过

### Step 2 — Core 平移纯计算

- [ ] 将 `PriceCalculator.cs`、`PriceRuleMapper.cs` **复制或移动**到 Core（移动后 Backend 改 ProjectReference）
- [ ] 命名空间：可保持 `CloudWarehouse.Backend.Helpers` 以减少 diff，或统一为 `CloudWarehouse.Pricing.Core`

### Step 3 — Backend 模块文件夹平移

- [ ] 按 §4 映射，分批移动（建议顺序：MasterData → Pricing → Import）
- [ ] 每移一批：`dotnet build` + 相关集成测试
- [ ] `Program.cs` 的 DI 注册仅改类型路径，**不改注册逻辑**

### Step 4 — 可选学术演示

- [ ] 新建 `CloudWarehouse.Pricing.Api`（最小 Web API，`POST /calculate` 调用 Core）
- [ ] **不**加入 `publish-self-contained.ps1` 输出

### Step 5 — 全量回归

- [ ] `dotnet test`

- [ ] `.\scripts\publish-self-contained.ps1` → 确认 zip 仍单 exe + bat

## 7. NUS 报告用架构叙述要点（复制进报告）

### 7.1 一句话定位

> We deliver a **modular monolith** for the industry partner (single Windows executable, SQL Server), while structuring code into **bounded contexts** (Master Data, Pricing, Import, Billing) that align with a **documented microservice evolution path** for academic evaluation.

### 7.2 当前态 vs 目标态

| 维度 | 当前（生产） | 学术「演进目标」 |
|------|--------------|------------------|
| 部署 | 1 进程 + 1 数据库 | Import / Billing 可拆为独立 HTTP 服务 |
| 通信 | 进程内方法调用 | 未来 REST + 共享 Pricing.Core |
| 数据 | 单库多表 | 可先逻辑分 schema，物理分库最后阶段 |
| 约束 | 师傅无 Docker | 演示环境可用 Compose 跑 Pricing.Api |

### 7.3 建议报告插图（已有 PlantUML 可扩展）

- 沿用 `docs/diagrams/05-ddd-bounded-contexts.puml`，增加 **Billing** 包
- 新增「C4 容器图」两页：**As-Deployed（单体）** vs **To-Be（可选拆分）**
- ADR 一条：**ADR-MS-01 为何生产保持单体**

### 7.4 ADR 草稿（英文）

**Title:** Modular monolith for production; microservices as evolution, not day-one deployment  

**Context:** Industry partner requires offline Windows deployment without orchestration. NUS internship requires service boundary analysis.  

**Decision:** Implement bounded modules in one ASP.NET Core host; extract pure pricing rules to `CloudWarehouse.Pricing.Core`; optional standalone `Pricing.Api` for demonstration only.  

**Consequences:** Lower ops cost for partner; credible microservice narrative for coursework; shared core prevents duplicate business rules.

### 7.5 答辩口述（中文）

「师傅要的是能双击跑的账单系统，所以我们生产是模块化单体。NUS 要求的微服务，我们体现在 **边界划分、Core 抽取、和演进架构图**，并用可选 Demo API 证明 Pricing 可独立部署，而不是让师傅装五个服务。」

## 8. Phase 2 业务与 Refactor 的关系

| 工作 | 类型 | 顺序建议 |
|------|------|----------|
| Step 1 搭架子 | Refactor | **先做** |
| 运单表 + 取整 + 双轨计费 | 新功能 | Step 1 完成后，代码直接写在 `Modules/Billing` |
| 客户账户表 | 新功能 | `Modules/MasterData` |
| 客户报价 / 成本双价目 | 新功能 | `Modules/Pricing` + Core 扩展 |

**新功能开发同样遵守本文红线**；不要「顺便 refactor 改公式」。

## 9. AI 操作检查表（每步完成后勾选）

参见 [`refactor.constraints.ini`](./refactor.constraints.ini) `[self_check]` 段，或逐项回答：

1. 是否改了计费/取整/Excel 逻辑？ → 必须 **否**
2. 是否一次改超过 10 个文件且未 `dotnet build`？ → 必须 **否**
3. 是否动过 `Program.cs` / `appsettings` / `启动云仓.bat` / publish 脚本？ → 必须 **否**（Step 5 仅验证 publish，不改脚本）
4. 主项目是否引用 `Pricing.Api`？ → 必须 **否**
5. 演示项目是否只依赖 Core？ → 必须 **是**
