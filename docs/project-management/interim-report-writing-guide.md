2. Project Overview
The CloudWarehouse project is an internally developed logistics pricing management system designed to streamline freight rate administration for warehouse operations. The system addresses the inefficiencies associated with manual handling of supplier-provided Excel-based price lists, which often suffer from inconsistent formatting and complex tiered pricing structures. This interim report presents a comprehensive overview of the project's progress during a four-week internship at a software development organization, focusing on the successful delivery of Phase 1 functionalities and outlining the strategic roadmap for future enhancements.
The core business problem stems from the fragmented nature of master data (Sites, Destinations, Customers) and the lack of a standardized process for importing and validating multi-tiered freight pricing rules. Current practices lead to frequent human errors, difficulty in maintaining up-to-date rates, and an inability to perform instant freight cost simulations. To resolve these issues, the primary objectives for Phase 1 were to establish a robust database foundation, implement a flexible Excel import mechanism capable of parsing diverse formats (standard, legacy three-row headers, and destination matrix), develop a trial calculation engine for freight fees, and ensure code quality through automated testing and continuous integration. These deliverables have been successfully completed, as evidenced by a fully functional prototype running at http://localhost:5001.
The project scope for this phase is deliberately focused on a single-tenant, browser-accessible administrative interface deployed on a local SQL Server instance. Key in-scope features include CRUD operations for master data, the aforementioned Excel import functionality, and the freight trial calculation API. Out-of-scope items, deferred to Phase 2 or beyond, include order fulfillment workflows, deep integration with Warehouse Management Systems (WMS), production-grade authentication and authorization (RBAC), and high-availability deployment configurations. The primary stakeholder for this system is the warehouse operations or quotation administrator, who is responsible for managing pricing data and generating quotes. The author served as a solo full-stack developer, taking ownership of all aspects of the project lifecycle, including requirements analysis, system design, implementation, testing, and documentation.
A summary of the key deliverables achieved in Phase 1 includes a complete database schema with Entity-Relationship Diagram (ERD), a fully operational price table import feature with preview capability, a reliable freight trial calculation function, and a suite of over forty automated tests integrated into a GitHub Actions CI pipeline. This report will subsequently delve into the technical architecture, development methodology, risk management strategies, and quality assurance measures that underpinned this delivery. In direct response to mid-term review feedback, this document has been significantly expanded to provide greater depth in critical areas such as Domain-Driven Design (DDD), the modular monolith architectural style, and the planned evolution towards a Strategy Pattern for billing complexity, ensuring a thorough academic and practical exposition of the work conducted.
3. Technology Stack
3.1 Stack Overview
The CloudWarehouse system is built upon a carefully selected set of technologies designed to meet the specific demands of a logistics pricing management system within a constrained four-week development timeline. The backend is powered by ASP.NET Core 9 with C#, chosen for its robust performance, built-in dependency injection, and cross-platform capabilities, which facilitate rapid development and deployment. Data persistence is handled by Microsoft SQL Server, providing a reliable relational database management system, with data access orchestrated through Dapper, a lightweight Object-Relational Mapper (ORM). For frontend presentation, the system employs a static HTML/JavaScript interface, deliberately avoiding complex Single-Page Application (SPA) frameworks to accelerate delivery and align the project focus on backend architecture. Excel file processing, a core business requirement, is managed using the ClosedXML library, which supports both reading diverse supplier formats and generating standardized templates. The quality assurance pillar is supported by the xUnit testing framework, complemented by WebApplicationFactory for integration testing, ensuring comprehensive test coverage. Finally, the entire development lifecycle is automated through a GitHub Actions Continuous Integration (CI) pipeline configured to run on the ubuntu-latest runner, guaranteeing code quality with every commit.1
3.2 Layered Mapping (Presentation / API / Data)
The application follows a clear layered architecture that dictates the runtime flow of data and requests. The entry point is the Presentation Layer, consisting of static files (index.html, CSS, JavaScript) served from the wwwroot directory. User interactions from this static frontend initiate HTTP requests to the API Layer, which is composed of RESTful controllers (SiteController, DestinationController, CustomerController, ImportController, PriceRuleController). These controllers receive requests, perform basic validation, and delegate business logic to the Application Layer. This layer contains services such as PriceRuleImportService and PriceRuleCalculateService, which encapsulate the core import and calculation workflows. To execute these workflows, the services utilize a suite of Domain Helpers (ExcelHelper, PriceRuleMapper, PriceCalculator) for specific tasks like parsing, mapping, and computing freight. Finally, all persistent data operations are handled by the Data Access Layer, where Dapper executes parameterized SQL statements against the SQL Server database, completing the flow from user interface to persistent storage.1

4. System Use Cases & Business Modules
4.1 Actors
The CloudWarehouse system is designed with a clear boundary that distinguishes between internal users and external data providers. The primary actor, who performs all system operations, is the Warehouse Administrator (or Quotation Administrator). This actor is responsible for the core administrative functions of the system, including managing master data (Sites, Destinations, Customers), importing and validating supplier price lists, and executing freight trial calculations to generate quotes1. The administrator interacts directly with the system’s web-based interface to fulfill these responsibilities.
A secondary actor, existing outside the system boundary, is the Supplier. Suppliers are the source of the Excel-based price lists that contain the freight rate information. They do not interact with the CloudWarehouse system directly; their role is limited to providing the input data files. The system must be capable of parsing the diverse formats (standard, legacy three-row headers, destination matrix) that these suppliers may use, thereby insulating the administrator from the variability of external data sources1. This actor definition clarifies that the system’s automation is focused on internal workflow efficiency rather than creating a collaborative platform with external partners.

4.4 Use Case Prioritisation (MoSCoW)
Given the constrained four-week timeline for Phase 1, the MoSCoW prioritisation method was applied to ensure focus on delivering the minimum viable product (MVP) that solves the core business problem. This classification guides development effort and scope management1.
• Must-have: These are critical for the MVP and define its core value proposition. Without them, the system does not address the stated problem.
○ Price Table Import (UC-06, UC-07): The ability to ingest and process supplier Excel files is the fundamental automation replacing manual handling.
○ Freight Trial Calculation (UC-08): The instant quote generation capability is the primary output and validation mechanism for the imported pricing data.
○ Basic Master Data CRUD (UC-01, UC-03): Managing Sites and Destinations is essential as they are foreign keys for all pricing rules.
• Should-have: Important but not vital for the first release; their absence can be worked around in the short term.
○ Customer Management (UC-04): While B2B customer data is part of the master data model, for MVP purposes, it could be managed externally or deferred, as it is not directly used in the core price import and calculation flow.
• Could-have: Desirable features that have lower impact on the core functionality and can be easily added later.
○ Login / Authentication: Acknowledged as a security gap in the MVP, it was consciously deferred to Phase 2 to prioritize core feature delivery1.
• Won’t-have (this phase): Explicitly excluded from Phase 1 scope to maintain focus.
○ Order Fulfillment Workflows: This extends into Warehouse Management System (WMS) integration and operational processes beyond simple pricing and quotation.
○ Advanced Reporting or Analytics: Deferred for future enhancements.
This prioritisation reflects the strategic decision to build a focused, functional prototype that validates the core data pipeline and calculation engine, as outlined in the project overview1.

5. Four-Week Internship Project Roadmap
5.1 Methodology (Sprint cadence, capacity assumption)
The project adopted a four-week, sprint-based agile methodology to structure the development effort within the constrained internship timeline. Each sprint was defined as a one-week iteration, aligning with the typical academic week and allowing for focused, incremental delivery of the Minimum Viable Product (MVP). The planning approach assumed a weekly capacity dedicated to the project, with the primary goal of delivering a functional system by the end of the fourth sprint. This methodology facilitated regular progress checks, adaptation to unforeseen complexities, and a clear mapping of work to the project’s overarching milestones. The sprint cadence provided a predictable rhythm for development, testing, and documentation, ensuring that the project remained on track to meet its Phase 1 objectives.1
5.2 Sprint 1 — Foundation
The primary goal of Sprint 1 was to establish the foundational elements of the CloudWarehouse system, creating a stable base for subsequent development. The planned deliverables for this sprint included the creation of the database schema (schema.sql), the implementation of basic CRUD (Create, Read, Update, Delete) operations for master data entities (Sites and Destinations), the construction of a basic user interface shell, and a technical proof-of-concept (spike) for the Dapper data access layer.1
The completed user stories from this sprint, as documented in the project plan, focused on environment setup and core data management. These included tasks such as setting up the development environment, designing the Entity-Relationship Diagram (ERD), and implementing the initial API endpoints and UI components for managing sites and destinations.1 A key issue encountered during this sprint was the initial environment setup, which involved configuring the local SQL Server instance and ensuring compatibility with the .NET 9 SDK. This foundational work was critical, as it defined the data model and established the basic application structure that all subsequent features would build upon.1
5.3 Sprint 2 — Excel Import
Sprint 2 was dedicated to developing the core Excel import functionality, a central component of the system designed to address the business problem of inconsistent supplier price lists. The goal was to implement a flexible mechanism capable of parsing diverse Excel formats. The key deliverables achieved included the creation of a standard Excel template for suppliers, the development of parsing logic to handle both standard single-row headers and legacy three-row headers, and the implementation of a preview functionality that allows administrators to validate data before committing it to the database.1 The PriceCalculator was also developed during this sprint to provide real-time price calculations within the preview.1
The user stories completed in Sprint 2 centered on the import workflow, from template generation to data preview. However, this sprint experienced a significant time overrun, with actual hours exceeding estimates by 39%.1 This variance was directly attributable to the unforeseen complexities involved in parsing the supplier-provided three-row headers, which required sophisticated logic for column detection and alignment, as well as the effort to ensure dual-format compatibility (standard and legacy).1 The notes for this sprint highlight that the complexity of handling merged cells and inconsistent column structures in real-world Excel files consumed substantially more development time than initially anticipated.1
5.4 Sprint 3 — Pricing Rules and Trial Calculation
The objective of Sprint 3 was to enable the persistent storage of validated pricing rules and to implement the freight trial calculation API. This involved moving from a preview-only system to one that could reliably update the database and provide instant cost estimates. The deliverables included implementing transactional import to ensure data integrity (all-or-nothing commits), adding logic to auto-create missing Sites and Destinations during the import process to improve usability, extending the import to support the matrix format (where a default site is assumed), and finally, developing the calculate API endpoint.1
The user stories completed in this sprint focused on the "commit" phase of the import and the calculation engine. This included work on the PriceRuleImportService to handle database transactions and the PriceRuleCalculateService to query the stored PriceRules and compute fees based on weight tiers and overweight pricing.1 A notable decision implemented was the auto-provisioning of master data; if an imported price row referenced a site or destination not yet in the database, the system would create it automatically, streamlining the operator’s workflow despite increasing the complexity of the import service.1
5.5 Sprint 4 — Quality Assurance and Evidence
The final sprint, Sprint 4, was devoted to quality assurance, automation, and the compilation of evidence for the interim report. The goal shifted from feature development to hardening the system and demonstrating its reliability and completeness. The key deliverables included writing a comprehensive suite of unit and integration tests (totaling over forty tests), setting up the Continuous Integration (CI) pipeline using GitHub Actions, creating a complete set of architecture and design diagrams using PlantUML, and preparing the final project report and presentation materials.1
The completed user stories in this sprint were almost exclusively related to testing, CI/CD, and documentation. This included creating test projects (CloudWarehouse.Tests and CloudWarehouse.IntegrationTests), configuring the ci.yml workflow, and generating diagrams such as the ERD, logical architecture, and sequence diagrams.1 This sprint also absorbed some integration testing work that was initially planned for Sprint 3, contributing to the lower actual hours recorded for the previous sprint.1 The output of Sprint 4 was a fully tested, documented, and demonstrable system prototype.
5.6 Velocity and Re-estimation Notes
An analysis of the sprint velocity reveals a significant variance, primarily driven by Sprint 2. The total estimated hours for the four sprints were 198, while the actual hours totaled 211, resulting in an overall variance of +13 hours, or approximately +7%.1 The most substantial deviation occurred in Sprint 2, with an overrun of +17 hours (+39%). This was exclusively due to the unanticipated complexity of algorithmically detecting and parsing the legacy three-row Excel header format and ensuring robust column alignment.1
Following the completion of Milestone M2 (Import preview) at the end of Sprint 2, a re-estimation of the remaining work was conducted. This recalibration, informed by the lessons learned from the Excel parsing challenges, led to significantly improved accuracy in the subsequent sprints. Sprint 3 and Sprint 4 showed variances of -9% and -6% respectively, indicating that the estimation process became more reliable once the team (in this case, the solo developer) had a concrete understanding of the system’s complexity and their own working pace.1 The corrective action taken was to factor such complex parsing logic as a high-risk item requiring a dedicated technical spike in future estimations, and to emphasize the importance of the preview-before-commit workflow as a risk mitigation strategy.1

7.4 Variance Analysis
A textual analysis of the variances between estimated and actual hours provides critical insights into the project’s execution challenges and learning points. The most significant variance occurred in Sprint 2, which recorded a +39% overrun (17 additional hours). This substantial deviation is directly attributable to the unforeseen complexity involved in handling supplier-provided Excel files, specifically the parsing of legacy three-row headers and ensuring robust column alignment detection1. The initial estimate underestimated the effort required to design an algorithm that could automatically detect whether the header information was contained in a single row or spread across three merged rows, and then correctly map data columns despite inconsistent merging. This complexity, coupled with the need to maintain compatibility with the standard single-row header format, resulted in significant additional development and debugging time.
Conversely, Sprint 3 showed a -9% variance (5 hours under estimate). This underrun can be partially explained by the strategic decision to defer the completion of some integration tests originally planned for Sprint 3 to the dedicated quality assurance focus of Sprint 41. Furthermore, the foundational work on the PriceRuleMapper and transactional logic, though complex, proceeded more smoothly once the core import parsing challenges from Sprint 2 had been resolved.
The overall project variance of +7% is considered acceptable for a four-week MVP development cycle. Crucially, the experience gained from the Sprint 2 overrun led to a re-estimation of the baseline for subsequent sprints. The re-estimation process, informed by the actual velocity and a clearer understanding of the remaining work’s complexity, contributed to the improved accuracy seen in Sprints 3 and 4, where variances were contained within a ±10% range1.
7.5 Corrective Actions
Based on the variance analysis, particularly the lessons from Sprint 2, several corrective actions were implemented to mitigate similar risks in future work and enhance estimation accuracy. First, to address the root cause of format incompatibility, the project now provides a standard Excel template for suppliers. Promoting the use of this template reduces the likelihood of encountering the problematic three-row header format, thereby decreasing parsing complexity and potential errors1.
Second, the system incorporates a preview-before-commit workflow for all price table imports. This allows the administrator to visually verify the parsed data, including the detected header format and calculated prices, before finalizing the transaction. This step acts as a validation gate, catching potential parsing issues early and preventing erroneous data from being persisted, which indirectly mitigates rework effort1.
Finally, for future phases involving similarly ambiguous or complex tasks, the estimation process will incorporate dedicated technical spike time. Allocating time specifically for researching and prototyping solutions to high-risk items (like parsing novel file formats) before committing to a full implementation estimate will lead to more realistic planning and reduce the probability of major schedule overruns1. These corrective measures collectively aim to improve project predictability and maintain the disciplined tracking of development effort demonstrated in Phase 1.
8. Database ERD Core Structure
8.1 Design Goals
The database schema for CloudWarehouse was designed with several primary objectives in mind, directly addressing the core business problems identified in the project overview. The foremost goal was to achieve a clear separation between master data and pricing rules, ensuring that foundational entities like Sites, Destinations, and Customers could be managed independently of the complex, frequently updated freight rates1. This separation facilitates easier maintenance, auditing, and data integrity. A second critical design goal was to robustly support the multi-tiered and overweight pricing models inherent in supplier-provided Excel files. The schema needed to accommodate multiple weight tiers (e.g., 0-0.3kg, 0.3-0.5kg, up to 4-5kg) and a separate overweight pricing structure for parcels exceeding 5kg, all within a single logical shipping lane defined by a Site and a Destination1. Furthermore, the design incorporates temporal validity through an EffectiveDate field, allowing for historical tracking and future-dated price updates, which is essential for accurate freight calculations over time1.
8.2 Entity-Relationship Model
The core data model of CloudWarehouse is defined by four principal entities and their relationships, as visualized in the Entity-Relationship Diagram (ERD)1. The Sites entity represents the originating warehouse or distribution centers from which shipments depart. The Destinations entity encapsulates the target delivery locations, typically defined down to the city or district level. The Customers entity stores information for B2B clients who are the recipients of the shipments and associated invoices. The central and most complex entity is PriceRules, which stores the actual freight pricing logic. The relationships are straightforward yet foundational: a PriceRule must be associated with exactly one Site (the origin) and one Destination (the endpoint), forming the unique "lane" for pricing. While a Customer may be associated with a calculation request, the PriceRules themselves are defined independently of specific customers to allow for reuse across multiple clients1. This ERD forms the backbone of all data persistence and business logic within the system.
8.3 Table Specifications
The following table provides a detailed specification for each of the four core database tables, outlining their purpose, key columns, and unique constraints as implemented in the database/schema.sql1.
Table	Purpose	Key Columns	Unique Constraint
Sites	Stores information about originating warehouse or distribution sites.	SiteCode (unique identifier), SiteName, Status (active/inactive).	UQ_SiteCode ensures no duplicate site codes.
Destinations	Defines target delivery locations (provinces, cities, areas).	DestCode (unique identifier), Province, City, Area.	UQ_DestCode ensures no duplicate destination codes.

The design of the PriceRules table is particularly notable for its BillingType column, which dictates the interpretation of the MinWeight, MaxWeight, and UnitPrice fields, enabling a single table structure to handle both discrete weight brackets and continuous overweight pricing1.
8.4 PriceRules Cardinality (One Excel Row to Many Rules)
A fundamental and non-obvious aspect of the database design is the one-to-many cardinality mapping from a single row in the imported Excel price table to multiple entries in the PriceRules database table. This design is critical for accurately modeling the supplier's complex pricing schemes1. A typical Excel row for a given site-destination lane contains prices for seven consecutive weight tiers (e.g., 0-0.3kg, 0.3-0.5kg, 0.5-1kg, 1-2kg, 2-3kg, 3-4kg, 4-5kg) and a unit price for overweight shipments (>5kg). During the import process, the PriceRuleMapper.ToPriceRules method deconstructs this single row1. It creates seven separate PriceRules records with BillingType = 1 (Tier), each with the appropriate MinWeight and MaxWeight bounds and the corresponding UnitPrice from the Excel cell. An eighth PriceRules record is created with BillingType = 2 (Overweight), where MinWeight is 5, MaxWeight is set to a very high value (or NULL), and UnitPrice represents the cost per additional kilogram1. This mapping ensures the database internally represents the full granularity of the pricing model, which is essential for the precise calculations performed by the PriceCalculator.
8.5 Indexing Decision and Migration Script
A significant lesson learned during the development of Phase 1 pertained to database indexing, specifically concerning the PriceRules table. Initially, a unique index named IX_PriceRules_SiteId_DestId_EffectiveDate was created on the combination of (SiteId, DestId, EffectiveDate)1. This index was intended to optimize query performance for the most common lookup pattern: finding all rules for a specific lane on a given date. However, this design contained a critical flaw. By making the index unique on those three columns, it became impossible to insert the multiple PriceRules records (for the different weight tiers) that originate from a single Excel row for the same site, destination, and effective date1. This error manifested during import testing, where attempts to commit a price table would fail with a unique key violation.
The issue was diagnosed and rectified by creating a migration script, database/fix-price-rules-index.sql1. The corrective action involved dropping the incorrect unique index and replacing it with a non-unique index on (SiteId, DestId) only, or potentially a non-unique index on (SiteId, DestId, EffectiveDate)1. This change preserved the query performance benefits for lane-based lookups while allowing the necessary multiple records to coexist. This experience underscored the importance of aligning database index design with the actual data cardinality and business logic, and it reinforced the practice of managing schema changes through version-controlled SQL scripts.
9. Logical Architecture & Bounded Contexts
9.1 Architectural Style (Modular Monolith)
The CloudWarehouse system adopts a modular monolith architectural style for its Minimum Viable Product (MVP) phase. This decision is a deliberate architectural choice, justified by the specific constraints and goals of the four-week internship project. A modular monolith is characterized by a single deployable unit (a single CloudWarehouse.Backend project) that is logically partitioned into distinct, cohesive modules or bounded contexts. This approach provides the benefits of a monolithic architecture—such as simplified deployment, rapid iteration, and straightforward debugging—while introducing a clear separation of concerns that facilitates future evolution. The primary rationale for this choice stems from the project’s tight timeline, the solo developer team size, and the initial focus on delivering core functionality. The architecture is designed to be logically modular with well-defined boundaries, even though it remains physically unified in a single process, thereby paving the way for potential service extraction in Phase 2 without requiring a complete rewrite of the codebase.1

9.6 Justification for Monolith at MVP Stage
The choice of a modular monolith over a microservices architecture for the MVP is strongly justified by the project’s initial conditions. The primary drivers are development speed, operational simplicity, and resource constraints. A microservices architecture introduces significant overhead in terms of inter-service communication (network latency, serialization), distributed data management, independent deployment pipelines, and operational monitoring—all of which are disproportionate for a four-week project developed by a single individual. The monolithic approach allows for:
*   Rapid Iteration: Changes can be made across layers and compiled/deployed as a single unit, accelerating the feedback loop.
*   Simplified Debugging: The entire application runs in one process, making tracing execution and inspecting state straightforward.
*   Single Deployment Artifact: Deployment to the local development environment or a future server is a matter of running one application.
*   Strong Data Consistency: ACID transactions across the Sites, Destinations, and PriceRules tables are trivial to implement within a single database connection.
Crucially, this decision is not an abandonment of modern architectural principles but a strategic postponement. By applying DDD and consciously designing with bounded contexts and a modular code structure, the system is prepared for future extraction. The contexts defined in Section 9.4 (Master Data, Import, Pricing) are natural candidates to become independent microservices if and when the scale, team size, or deployment frequency justifies the added complexity. Therefore, the modular monolith represents an optimal balance for the MVP stage, delivering immediate value while preserving architectural flexibility for Phase 2 and beyond.1

12.3 ADR-2: Dapper for Data Access
• Status:Accepted
• Context:A core requirement was the efficient handling of bulk Excel price table imports, which involves parsing hundreds of rows, mapping them to multiple database records per row, and performing transactional upserts into thePriceRulestable. The system required fine-grained control over SQL statements, explicit transaction management, and optimal performance for write-heavy operations. The alternative, Entity Framework (EF) Core, offers rich features but can introduce abstraction overhead and generate complex SQL for bulk operations.1
• Decision:Use Dapper as the primary Object-Relational Mapper (ORM) instead of Entity Framework Core. All data access in controllers and services is implemented using rawSqlConnectionobjects and Dapper’s extension methods for querying and executing commands.1
• Consequences:
○ Positive:Provided maximum control and transparency over the SQL executed against the database, which was crucial for optimizing the import pipeline. Transaction management (BEGIN TRANSACTION,COMMIT,ROLLBACK) was straightforward and explicit, ensuring data integrity during the all-or-nothing import commits. Performance for the bulk insert operations was predictable and efficient.1
○ Negative:Required writing and maintaining more boilerplate SQL code compared to EF Core. Features like automatic change tracking, migrations, and LINQ-based query composition were not available, placing the burden of data mapping and schema evolution on the developer.
○ Evidence:The codebase contains no references to EF CoreDbContextorDbSet. Instead, data access layers consistently use patterns likeusing var connection = new SqlConnection(_connectionString)andconnection.ExecuteAsync(...).1
12.4 ADR-3: Excel-Only Price Rule Authoring
• Status:Accepted
• Context:The primary source of pricing information is external suppliers who provide freight rates in Excel spreadsheets. The business workflow is centered around receiving, validating, and importing these files. Creating a separate, fully-featured CRUD interface for manually defining complex tiered pricing rules (e.g., 0-0.3kg, 0.3-0.5kg, ..., >5kg) would be time-consuming, error-prone, and misaligned with the established supplier-to-warehouse data exchange process.1
• Decision:Price rules can only be created and updated via the Excel import functionality. The system does not expose aPOST /api/PriceRuleendpoint or a UI form for manual rule entry. Rule authoring is delegated to the Excel template and the parsing logic.1
• Consequences:
○ Positive:The system interface perfectly mirrors the real-world business process, reducing friction for the warehouse administrator. It forces data standardization through the provided Excel template. Development effort was focused on perfecting a single, robust import path rather than splitting efforts between import and manual CRUD.
○ Negative:Administrators have no way to correct a single erroneous price rule within the system without re-importing an entire Excel file (though they could edit a small template). The system is dependent on the correctness of the external Excel parsing logic.
○ Evidence:ThePriceRuleControllerlacksCreateorUpdateactions. The only way to persist rules is through theImportControllerendpoints (/api/Import/price-table/previewand/api/Import/price-table).1
12.5 ADR-4: Multi-Row PriceRules per Import Line
• Status:Accepted
• Context:Supplier pricing models involve both tiered pricing for parcels ≤5kg (split into multiple weight brackets) and overweight pricing for parcels >5kg (a base fee plus a per-kilogram charge). A single Excel row from a supplier’s price list defines the rates for all these brackets for a specific lane (Site→Destination) and effective date. The database model must faithfully represent this complexity to enable accurate freight calculations.1
• Decision:Implement a one-to-many mapping from a single importedPriceTableRowto multiplePriceRulesdatabase records. The mapping logic, encapsulated inPriceRuleMapper.ToPriceRules, generates up to eightPriceRuleentries per Excel row: seven for the tiered brackets (BillingType = 1) and one for the overweight rule (BillingType = 2).1
• Consequences:
○ Positive:Accurately captures the full supplier pricing model in a normalized database schema. Enables the freight calculation engine (PriceCalculator) to perform simple, efficient queries to find the applicable rule based on weight. The design is extensible to support future billing types.
○ Negative:Increases the complexity of the import process, as parsing a 100-row Excel file could result in up to 800 database insertions. This necessitated careful transaction design and performance consideration, reinforcing the choice of Dapper (ADR-2). It also led to an initial database design error where a unique index incorrectly prevented multiple rules for the same lane and date, requiring a corrective migration script (fix-price-rules-index.sql).1
○ Evidence:ThePriceRulestable schema includesBillingType,MinWeight, andMaxWeightcolumns. ThePriceRuleMapper.csfile contains the explicit logic for generating the multiple rule records. A screenshot from SSMS shows multiplePriceRulesentries with the sameSiteIdandDestIdbut different weight boundaries.1
13. Architecture Decision Records (ADR) — Part 2: Trade-offs
This section documents the second set of critical architectural decisions for the CloudWarehouse project, focusing on trade-offs made to balance business needs, technical feasibility, and project constraints during the Minimum Viable Product (MVP) phase. These decisions address operational risks, usability concerns, and the strategic planning for future complexity.
13.1 ADR-5: Dual-Header and Matrix Excel Auto-Detection
• Status:Accepted
• Context:Suppliers provide freight price lists in various Excel formats, including a standard single-row header, a legacy three-row header (where column names are split across multiple rows), and a destination matrix format (where destinations are listed as columns against a default site). Enforcing a single, rigid template was deemed impractical as it would create significant support burden and resistance from suppliers accustomed to their existing formats1.
• Decision:The system implements an auto-detection mechanism within theExcelHelperclass to intelligently parse these diverse formats without requiring manual column mapping from the user1. The algorithm scans the first few rows of the uploaded file for known keywords (e.g., “生效时间” for effective date, “目的地” for destination) to determine theheaderRowanddataStartRow1. For the matrix format, it defaults to a pre-configured site code (e.g., C001) when no site column is present1.
• Consequences:
○ Positive:Dramatically improves usability and adoption by accommodating real-world supplier workflows. The preview functionality allows administrators to verify parsing correctness before committing data1.
○ Negative:Increased implementation complexity and testing surface area. Parsing logic is more fragile and requires comprehensive unit tests (e.g.,ExcelHelperTests) to handle edge cases1. Time overrun in Sprint 2 (+39%) was directly attributed to developing this compatibility1.
○ Evidence:The auto-detection logic is central to the price import use case (UC-06/UC-07). Its success is evidenced by screenshots of successful imports from matrix-format tables1.
Rejected Options:
| Option | Rejected Because |
| :--- | :--- |
| Enforcing a single standard template only | Suppliers are unlikely to adopt a new format, leading to manual data entry or system bypass, defeating the purpose of automation1. |
| Building a manual column mapping UI for each upload | This feature was considered out of scope for the four-week MVP, as it would add significant frontend and state-management complexity1. |
| Chosen: Auto-detect row 1 vs row 3 + matrix | This option struck the best balance between user compatibility and development effort within the MVP timeline1. |
13.2 ADR-6: Auto-Provision Master Data on Price Import
• Status:Accepted
• Context:Price rule Excel files may reference sites and destinations that do not yet exist in the master database. Requiring administrators to pre-populate all master data manually before every import creates friction, slows down the pricing update process, and is particularly problematic for matrix-style sheets which may not even list a site column1.
• Decision:During the transactional commit phase of price import, thePriceRuleImportServicechecks each referenced site and destination code. If a code is missing from theSitesorDestinationstables, the service automatically creates a new record with a default name and status1. This “auto-provisioning” ensures the import can proceed to completion.
• Consequences:
○ Positive:Greatly enhances user experience and operational efficiency. It allows for rapid ingestion of new pricing data even for new lanes (site-destination pairs). The import summary clearly reports the count ofsitesCreatedanddestinationsCreated1.
○ Negative:Introduces potential data quality issues, as auto-created records may have placeholder names (e.g., “Site C001”) that require later cleanup. It also increases the complexity of the import service, which must handle master data creation within the same transaction as rule insertion1.
○ Evidence:This behavior is a key part of the import flow described in Section 14. The import result DTO includes fields specifically forsitesCreatedanddestinationsCreated1.
Rejected Options:
| Option | Rejected Because |
| :--- | :--- |
| Strict validation rejecting imports with missing master data | This would force a cumbersome two-step process (first add master data, then import prices), degrading usability and efficiency for the primary user1. |
| Chosen: Auto-create missing Sites/Destinations on import | Prioritized user workflow smoothness and MVP delivery speed, accepting the trade-off of potentially “dirty” master data that can be refined later1. |
13.3 ADR-7: Deferred Authentication (MVP)
• Status:Accepted (Deferred to Phase 2)
• Context:The primary goal of Phase 1 was to deliver core freight rate management functionality within a constrained four-week timeline for a solo developer1. Implementing a production-grade authentication and authorization system (e.g., JWT tokens, Role-Based Access Control) is a non-trivial feature that involves frontend login pages, backend security middleware, user management, and secure password storage.
• Decision:Authentication and authorization were consciously deferred to Phase 21. The Phase 1 MVP runs with no authentication, accessible to anyone on the local network. A permissive CORS policy (AllowAll) is configured inProgram.csfor development convenience1.
• Consequences:
○ Positive:Enabled the team to focus all development effort on the unique business logic of price import and calculation, which are the core value propositions of the system. This was critical for achieving a demonstrable prototype within the internship period1.
○ Negative:Represents a significant security risk for any deployment beyond a local development machine. The system is vulnerable to unauthorized access and data modification1. This is explicitly documented as a known limitation and a key item in the risk register (Risk S1)1.
○ Evidence:The infrastructure inventory in Section 10 states the MVP uses HTTP only on localhost with no TLS termination1. The risk register in Section 17 provides a detailed comparative analysis of mitigation plans for Phase 21.
Rejected Options:
| Option | Rejected Because |
| :--- | :--- |
| Implementing full JWT/RBAC authentication in Phase 1 | This would have consumed a disproportionate amount of the limited sprint capacity (likely an entire sprint), jeopardizing the delivery of core business features1. |
| Chosen: Defer authentication to Phase 2 | This aligned with the MVP philosophy of prioritizing “Must-Have” functionality (MoSCoW from Section 4) and allowed for a focused delivery of the price management system1. |
13.4 ADR-8: Billing Strategy Pattern (Planned)
• Status:Proposed (For Phase 2)
• Context:The current Phase 1 system handles two billing types: tiered pricing for weights ≤5kg (BillingType=1) and overweight pricing for weights >5kg (BillingType=2)1. Business requirements indicate future needs for more complex billing variants, such as volumetric weight calculation, step pricing, irregular parcel surcharges, and late payment penalties1. Hardcoding these new rules into the existingPriceCalculatorclass would lead to a large, complex, and difficult-to-maintain method riddled withif-elseorswitchstatements.
• Decision:To manage this anticipated growth in billing complexity, it is formally proposed to refactor the pricing engine in Phase 2 using theStrategy Pattern1. This involves defining a commonIBillingStrategyinterface with aCalculate(context)method. Each billing variant (Tier, Overweight, Volumetric, etc.) would be implemented in its own concrete strategy class (e.g.,TierBillingStrategy,VolumetricBillingStrategy)1.
• Consequences:
○ Positive (Planned):Encapsulates each billing algorithm, making the system extensible. New billing types can be added by creating a new strategy class without modifying existing logic (Open/Closed Principle)1. Improves code testability and maintainability. Clearly links to the Phase 2 milestone M6 (“Billing Strategy Pattern”)1.
○ Negative (Planned):Introduces some initial refactoring overhead. Requires design of a strategy selection mechanism (e.g., a factory mappingBillingTypeenum to strategy instances) and potentially a more complex context object to pass necessary data1.
○ Evidence:This decision is a direct response to mid-term supervisory feedback requesting deeper consideration of billing complexity1. It is elaborated in Section 20.2 (Billing Complexity Analysis table) and Section 20.3, which includes a textual class diagram description and a three-step extension process1.
Rejected Options:
| Option | Rejected Because |
| :--- | :--- |
| Continuing with monolithic if-else logic in PriceCalculator | This approach becomes unmanageable and error-prone as the number of billing variants increases, directly conflicting with the need for a maintainable system in Phase 21. |
| Chosen: Adopt Strategy Pattern in Phase 2 | This pattern is a classic and appropriate solution for dynamically selecting an algorithm, providing a clear path to manage future billing complexity1. |

14. Core Use Case Execution Flow
14.1 Primary Use Case: Price Table Import (UC-06/UC-07)
The price table import functionality is identified as the primary use case for detailed examination, as it represents the most complex and critical business process within the CloudWarehouse system. This process, encompassing both preview (UC-06) and commit (UC-07) phases, directly addresses the core business problem of ingesting supplier-provided Excel price lists with inconsistent formatting and complex tiered pricing structures. The successful implementation of this use case validates the system’s ability to handle real-world data variability and ensure data integrity through transactional operations.1
14.2 Normal Flow (Step-by-Step)
The normal execution flow for the price table import process is a meticulously designed sequence of steps that ensures data validation, user confirmation, and atomic database operations. The following twelve-step flow details the journey from file selection to final database persistence.1
1. File Selection:The Warehouse Admin navigates to the “Import” tab within the single-page administrative interface and selects a.xlsxor.xlsmfile using the provided file input control.1
2. Preview Request:The browser initiates aPOSTrequest to the/api/Import/price-table/previewendpoint, transmitting the selected file as multipart form data.1
3. Initial Validation:TheImportControllerreceives the request and performs initial validation checks, including verifying the file extension against a whitelist (.xlsx,.xlsm) and enforcing a size limit (e.g., 10 MB) to mitigate technical risks associated with large uploads.1
4. Service Invocation:Upon successful validation, the controller delegates the processing to thePriceRuleImportService.ProcessImportAsync(save=false)method, passing the file stream and indicating this is a preview operation.1
5. Format Detection and Parsing:ThePriceRuleImportServiceutilizes theExcelHelper.ReadPriceTablemethod. This helper performs automatic format detection by scanning the first few rows (1–5) for known header patterns such as “生效时间” (effective date) or “目的地” (destination). It successfully identifies whether the file conforms to the standard single-row header, the legacy three-row header, or the destination matrix format (which lacks a site column and defaults to siteC001). Based on the detectedheaderRowanddataStartRow, it parses the spreadsheet into a collection ofPriceTableRowobjects.1
6. Price Calculation and Preview Assembly:For each parsedPriceTableRow, the service employs thePriceCalculatorto compute the expected freight cost based on the row’s weight tiers, providing immediate validation feedback. The service then resolves the correspondingSiteIdandDestinationIdfor each row by querying the master data tables. If a site or destination code from the Excel file does not exist in the database, it is added to aMasterDataToCreatelist for user awareness. A comprehensive preview object is assembled, containing the parsed rows, calculated prices, and a summary of any missing master data.1
7. UI Rendering:The preview response is sent back to the frontend. The user interface renders a detailed table showing each row, its parsed values, the calculated price, and highlights any rows requiring master data creation. A summary section clearly informs the admin of the number of rows parsed, lanes affected, and potential new sites/destinations.1
8. User Confirmation:The Warehouse Admin reviews the preview data. If correct, they click the “Confirm Import” button. If errors are spotted, they can cancel and upload a corrected file.1
9. Commit Request:Upon confirmation, the browser sends aPOSTrequest to the/api/Import/price-tableendpoint, typically sending a unique session identifier or the validated preview result payload.1
10. Transactional Database Operations:TheImportControlleragain callsPriceRuleImportService.ProcessImportAsync(save=true). This time, the service executes within a database transaction (SqlTransaction). The flow within the transaction is:1a.Ensure Master Data:For each item in theMasterDataToCreatelist, the service callsEnsureSiteorEnsureDestinationmethods, which perform anUPSERT(INSERT if not exists, otherwise SELECT) operation, guaranteeing the requiredSiteIdandDestinationIdare available.1b.Delete Existing Rules:For each unique lane (SiteId, DestId) and effective date present in the import batch, any existingPriceRuleswith that same lane and date are deleted (DELETE FROM PriceRules WHERE SiteId=@s AND DestId=@d AND EffectiveDate=@e). This ensures idempotency and versioning of price lists.1c.Insert New Rules:Each validatedPriceTableRowis passed to thePriceRuleMapper.ToPriceRulesmethod. This critical component implements the one-to-many mapping defined in ADR-4, transforming a single Excel row into multiplePriceRuleentities. For weights ≤5kg (BillingType = 1), it creates up to seven distinct records for predefined weight tiers (e.g., 0–0.3kg, 0.3–0.5kg, …, 4–5kg). For overweight pricing (>5kg,BillingType = 2), it creates a rule with aUnitPricerepresenting the cost per additional kilogram. All generatedPriceRuleentities are then bulk-inserted into the database.1d.Commit Transaction:If all operations succeed, the SQL transaction is committed. If any error occurs (e.g., constraint violation, connection loss), the transaction is rolled back entirely, leaving the database in its pre-import state.1
11. Commit Response:The service returns a detailed result object (PriceTableImportResult) containing metrics such aslanesUpserted,rulesUpserted,sitesCreated, anddestinationsCreated.1
12. Success Notification:The UI receives the response and displays a success message to the admin, summarizing the impact of the import operation.1
14.3 Alternative and Exception Flows
The system incorporates robust handling for alternative and exception scenarios to ensure reliability and user guidance. The following table documents the key alternative flows and their corresponding system behaviors.1
Condition	System Behaviour
Row Validation Error on Commit	If any PriceTableRow fails business validation during the commit phase (e.g., invalid numeric format, missing required column), the entire database transaction is rolled back. The API returns a 400 Bad Request response with an ApiResponse object containing a detailed error message, including the row number and a description of the validation failure. No partial data is persisted.1

Invalid File Extension	The ImportController validation rejects files with extensions not in the whitelist (e.g., .txt, .pdf). It returns a 400-style error message within the ApiResponse structure, informing the user that only Excel files are accepted.1

Matrix Format Detection	When the ExcelHelper detects the matrix format (characterized by the absence of a site column), it automatically assigns a default site code (e.g., C001) to all parsed rows. This logic is part of the auto-detection and auto-provisioning strategy documented in ADR-5 and ADR-6.1

Database Connection Failure During Preview	If the database is unavailable during the preview request, the service cannot resolve Site/Destination IDs. In this case, the preview operation proceeds in a “parse-only” mode. A warning is included in the preview result indicating that master data resolution was skipped, and the admin is advised to verify site/destination codes manually before commit.1

Transaction Rollback on Failure	As a core integrity measure, the entire import batch is wrapped in a SQL transaction. Any exception during the EnsureSite, Delete, or Insert steps triggers a rollback. The UI displays a generic “Import failed” message, and system logs capture the specific SQL exception for debugging. The state of the PriceRules table for the affected lanes remains unchanged.1


14.4 Secondary Use Case: Freight Trial Calculation (UC-08)
The freight trial calculation use case provides immediate business value by allowing the admin to simulate shipping costs. Its execution flow is more streamlined compared to the import process. The admin navigates to the “Trial Calculation” tab and fills a form with parameters: Site, Destination, Customer (optional), Parcel Weight, and Date. It then determines the applicable BillingType: if the parcel weight is ≤5kg, it selects the corresponding tiered rule and calculates cost as BaseFee; if the weight is >5kg, it selects the overweight rule and calculates cost as BaseFee + (Weight - 5) * UnitPrice. The calculated total fee is returned to the UI and displayed clearly to the admin.1

The quality assurance (QA) strategy for the CloudWarehouse project is structured around the classic Test Pyramid model, which prioritizes a broad base of fast, isolated unit tests, a middle layer of integration tests that verify component interactions, and a smaller apex of end-to-end or stress tests 1. This approach ensures a balance between development speed, test reliability, and confidence in system behavior. The pyramid is implemented across three dedicated test projects within the solution, each targeting a specific testing scope. The overall strategy is integrated into the development lifecycle, with automated test execution mandated for every code change via the Continuous Integration (CI) pipeline defined in .github/workflows/ci.yml 1. This ensures that quality is not a final-phase activity but a continuous process, directly addressing the project objective of ensuring code quality through automated testing 1.

20.3 Planned Strategy Pattern Design
To address the burgeoning billing complexity, a refactoring to the Strategy Pattern is formally planned for Phase 2. This design pattern defines a family of algorithms (billing strategies), encapsulates each one, and makes them interchangeable. The BillingContext can then delegate the calculation to a concrete strategy without being aware of its internal logic.1
Textual Class Diagram:
- IBillingStrategy (Interface): Declares the common Calculate(BillingContext context): decimal method.
- TierBillingStrategy (Concrete Strategy): Implements the calculation for weight-tiered pricing as currently defined in PriceCalculator.
- OverweightBillingStrategy (Concrete Strategy): Implements the base fee + per-kg calculation for overweight parcels.
- VolumetricBillingStrategy, StepBillingStrategy, ... (Future Concrete Strategies): Implement their respective billing algorithms.
- BillingContext: Maintains a reference to an IBillingStrategy object and is configured with the appropriate strategy based on the BillingType or other rule attributes. It provides the Calculate() method that delegates to the current strategy.
- BillingStrategyFactory: Responsible for creating and returning the correct concrete strategy instance based on input parameters (e.g., BillingType enum, rule metadata).
Three-Step Extension Process for New Billing Types:1
1.  Implement IBillingStrategy: Create a new class (e.g., VolumetricBillingStrategy) containing the specific calculation logic.
2.  Register in Factory/DI: Update the BillingStrategyFactory or Dependency Injection container to map a new BillingType enum value (e.g., BillingType.Volumetric) to the new strategy class.
3.  Update Rule Mapping: Ensure the PriceRuleMapper or import logic can correctly assign the new BillingType to price rules parsed from Excel.
This design ensures that adding a new billing variant does not require modifications to the core BillingContext, PriceRuleCalculateService, or existing strategies, adhering to the Open/Closed Principle.

The decision to split the modular monolith into independent microservices will be driven by specific, quantifiable operational and organizational factors, not merely architectural trends.1 The following conditions are identified as potential triggers:
1. Team Size & Structure: The development team grows beyond 3-4 Full-Time Equivalents (FTEs) working on the same codebase, leading to coordination overhead and merge conflicts.
2. Independent Scaling Requirements: Metrics indicate that one bounded context (e.g., the Import module) requires significantly more computational resources or has different scaling patterns compared to others (e.g., the low-latency Pricing API).
3. Deployment Frequency Conflict: The need to deploy bug fixes or minor enhancements to the Pricing logic weekly conflicts with the slower, more rigorous release cycle required for the core Master Data domain.
4. Technology Heterogeneity Need: A compelling case arises to use a different technology stack for a specific context (e.g., using Python for advanced data processing in the Import service while the core remains in C#).
5. Quantified Performance Demand: The freight trial calculation endpoint (/api/PriceRule/calculate) sustains a Query Per Second (QPS) rate exceeding a predefined threshold (e.g., 50 QPS), indicating a need for dedicated, optimized infrastructure.

20.7 Known Limitations
Honest acknowledgment of the current Minimum Viable Product's limitations is crucial for setting correct expectations and guiding future development priorities.1
1. No Authentication/Authorization: The MVP runs with no user authentication, relying on network isolation (localhost). This is unsuitable for any multi-user or production deployment.
2. Permissive CORS Policy: The development configuration uses a permissive Cross-Origin Resource Sharing (CORS) policy (AllowAll), which presents a security risk if exposed.
3. Single-Node Deployment: The application and database run on a single node with no redundancy, load balancing, or high-availability configuration.
4. Lack of Chunked Uploads: Large Excel file uploads are handled in memory with a 10MB hard limit; streaming or chunked uploads for very large files are not implemented.
5. Basic Error Handling for Complex Formats: While auto-detection for dual headers exists, the error messages for malformed supplier files could be more user-friendly.
6. Mixed Language UI Messages: Some backend validation messages are in Chinese, while the UI is primarily English, creating a minor inconsistency.
