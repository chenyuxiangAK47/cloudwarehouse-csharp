# 第九章 风险管理

Risk Management

第八章说明了质量与安全如何被流水线约束；本章从 **项目 / 技术 / 安全** 三类风险说明：识别了什么、采取了何种缓解、哪些仍属规划，以及如何用证据证明缓解有效。风险治理与四周 Sprint 节奏绑定：每个 Sprint 开始时回顾登记册，把缓解动作写进当周 Must 任务，而不是事后补写漂亮表格。

图示：`docs/diagrams/12-risk-management.puml`；答辩一页口述见 `docs/project-management/risk-management-slide.md`。

---

## 9.1 风险管理方法

| 步骤 | 本项目做法 |
|------|------------|
| 识别 | 从 Excel 导入失败、CI 环境差异、演示暴露面等真实事件抽象风险项 |
| 评估 | 定性矩阵：可能性 × 影响（见 9.5） |
| 缓解 | 能在 MVP 内关闭的立即做（预览、事务、白名单、CI）；需产品决策的写入 ADR 与 Planned |
| 跟踪 | 与里程碑、个人工时偏差联动（如 R1 ↔ Sprint 2 +39%） |

本项目为 **Solo** 实习：风险登记与工时统计均为个人维度。导师要求中“新加入开发者从某 Sprint 起单独统计”——**本项目无第二名开发者加入，该项记为 N/A**，避免虚构团队产能。

## 9.2 项目风险（Project）

| ID | 风险 | 影响 | 已实施缓解 | 后续 / Phase 2 |
|----|------|------|------------|----------------|
| R1 | Sprint 2 因遗留三级表头等 Excel 复杂度超支（实际 +39%） | 挤压后续 Sprint | 预览后提交；Sprint 2 后重估；外部文件类任务预留缓冲 | 同类集成任务继续留缓冲 |
| R2 | Solo 范围蔓延（手工规则 CRUD、提前上认证、过度画图等） | 质量下降、核心延期 | MoSCoW；ADR 锁范围（如 Excel 写规则、认证延期） | 继续 ADR + backlog 纪律 |
| R3 | 本地 SQL Server 与 CI 环境漂移 | “本机能过、流水线红/假绿” | 版本化 `database/*.sql`；GitHub Actions 强制 `dotnet test`；无库时依赖库用例可解释跳过 | 保持 schema 与测试同步 |

**R1 效果：** 超支集中在 Sprint 2；Sprint 3–4 回到约 ±10% 偏差（见第四章工时表），说明复盘纠正有效。

## 9.3 技术风险（Technical）

| ID | 风险 | 影响 | 已实施缓解 | 后续计划 |
|----|------|------|------------|----------|
| T1 | 遗留三级表头错列 → 错价 | 报价/结算错误 | `ExcelHelper` 自动探测表头行；标准模板下载；单元测试覆盖双格式 | 极端乱表可规划列映射 UI |
| T2 | 导入部分成功导致同 lane 新旧规则混杂 | 数据完整性破坏 | `SqlTransaction`：校验/写入失败整批回滚（ADR-4） | 当前规模下机制已够用 |
| T3 | 超大 Excel 导致内存/超时 | 不可用、体验差 | 扩展名白名单 + 体积上限（如约 10MB） | **规划**：流式/分块读取、后台作业、断点续传——**本期未实现**，勿写成已做 |
| T4 | `(SiteId, DestId, EffectiveDate)` 错误唯一索引阻断一对多档位入库 | 导入失败 | `database/fix-price-rules-index.sql` 删除错误唯一索引；索引与一对多基数对齐 | 变更继续走脚本，禁止口头改库 |

T1 与 R1 同源：技术复杂度直接转化为进度风险。T4 是索引设计与业务基数不一致的典型课，已在第五章数据库决策中交叉引用。

## 9.4 安全风险（Security）

| ID | 风险 | 影响 | 当前缓解（MVP） | 规划 |
|----|------|------|-----------------|------|
| S1 | API/UI **无认证授权** | 若暴露出本机则数据可被篡改 | 演示默认本机/受控内网；ADR 明确延期认证 | JWT + RBAC（见下对比） |
| S2 | CORS `AllowAll`（开发便利） | 跨源部署时攻击面扩大 | 文档标明仅为开发配置 | 生产收紧为明确 Origin 白名单 |
| S3 | 连接串等密钥、Excel 上传面 | 凭证泄露 / 恶意文件 | `.gitignore` / `appsettings.example.json`；上传白名单与大小限制；CI CodeQL + 依赖脆弱列表 | User Secrets / Key Vault；上线前 HTTPS |

### S1 方案对比（回应导师“给出两种可选方案”）

| 准则 | 方案 A：对接既有 WMS/企业 SSO | 方案 B：独立 JWT + RBAC |
|------|-------------------------------|-------------------------|
| 集成成本 | 高，依赖外部 IdP 与联调窗口 | 中，本系统内用户与角色 |
| 账号管理 | 集中在企业侧 | 本系统维护 |
| 演示独立性 | 依赖企业测试环境 | 可独立演示 |
| 建议 | 若云仓必须嵌入既有 WMS 生态再优先 | **默认推荐 Phase 2 路径**：独立可控，契合当前 Modular Monolith |

## 9.5 风险矩阵（缓解前定性）

|  | 低影响 | 中影响 | 高影响 |
|--|--------|--------|--------|
| **高可能** |  |  | T1 遗留表头 |
| **中可能** | S2 CORS | R1 进度超支；T3 大文件 | S1 无认证（一旦外网暴露则高影响） |
| **低可能** | S3 密钥（有示例脱敏习惯时） | R2 范围；T2 部分导入（有事务后更低） |  |

解读：T1 在开发期最“真”——已体现为 Sprint 2 超支；S1 在 localhost 演示期可能性受控，但 **任何对外部署前必须关闭**。

## 9.8 本章小结

本章表明风险不是附录装饰：R1 用数据证明被遏制，T1/T2/T4 用代码与脚本关闭，S1 用方案对比承认缺口。下一章将把中期导师意见 **逐条映射** 到已落地的设计、架构、证据与本章风险动作，形成终稿最核心的“答卷页”。
